## 2026-10-02 — Correction: the long-form Traditions source must carry all twelve; Tradition 12 was recovered from p0258

## 2026-10-02 — Reference texts are derived from the committed Big Book corpus by one extraction script; the long-form Traditions source ships all twelve (12 ships after correction — see entry above)

**Context:** Implementing `add-recovery-reference-texts`, the Steps, long-form Traditions, Promises, and Third/Seventh Step prayers all already exist in `big-book-2ed`. [Originally this entry recorded an 11-of-12 ship on the false premise that Tradition 12's sentence was "cut off mid-page"; that rationale was wrong — the two passages are cleanly contiguous. ## 2026-10-02 — Small reference sources exposed a test-search ranking assumption; the guard is now scoped to groups that actually contain an adjacent match

**Context:** After indexing the 2-passage `twelve-steps` and 3-passage `promises-and-prayers` sources, `pnpm run test:search` failed one ranking test. Its loop over every source group for the query `self will` asserted `group.results.length > 1` and that the top result is adjacent (`proximityWindow === 2`). Those hold for the large Big Book/12&12/DR sources but are simply false for a small source whose only matches are non-adjacent (the Third Step prayer contains "self" and "will" but not adjacent).
**Choice:** Keep the real invariant — an adjacent match outranks a non-adjacent one — but scope it to groups that actually contain an adjacent result, and skip single-result groups (ordering is vacuous there). `scripts/test-search.mjs` is test tooling, not app code, so this stays on the corpus path; no `src/` file changed.
**Trade-offs:** The test no longer asserts that every source has >1 result for `self will`, which was incidental to the invariant it meant to check. A genuinely mis-ranked adjacent match in a small source is still caught, because the guard runs whenever an adjacent result exists.
**Revisit:** If the source set grows or the query fixture changes, re-confirm the guard still exercises at least one multi-result group per source family.

## 2026-10-01 — Adopt Playwright (Chromium, headless) as the browser-verification layer

**Context:** Two shipped UI changes (`search-qol-improvements`, `passage-reader-controls`) plus several earlier ones each carried `manual (browser)` tasks that could not be run because the repo had no headless browser — and this session proved why that gap mattered: the first Playwright run immediately surfaced a PRODUCTION bug (full-text passage pages threw `effect_update_depth_exceeded` in a self-triggering `$effect`, pre-existing since `c43ff54`) that build/`check`/unit tests structurally cannot catch. The host had no Playwright, but pnpm + the npm registry + `~/.cache/ms-playwright` (chromium already cached) and the needed system libs were all present.
**Choice:** Add `@playwright/test@1.63.0` as a devDependency and an `e2e/` suite (`playwright.config.ts`, `pnpm run test:e2e`) that boots a FRESH Vite dev server on `PLAYWRIGHT_PORT` (default 5173) with `reuseExistingServer: false` and Chromium headless, `workers: 1`. Browser APIs the app depends on (`speechSynthesis`/`SpeechSynthesisUtterance`, `navigator.clipboard`) are mocked via `addInitScript` so tests are deterministic and never pass on the mock alone (assertions check the app actually called `speak`/`pause`/`resume`/`cancel`/`writeText`). "No network" scenarios assert ZERO requests (third-party GA/Fonts noise is blocked from the measured interaction), not a substring denylist. The suite also carries an explicit effect-loop `pageerror` regression guard.
**Trade-offs:** ~36 tests and a devDependency enter the repo, and `test:e2e` is slow (~1 min) and not wired into CI yet (no workflow). Pixel-level visual/contrast review, real audio output, and OS clipboard integration remain genuinely manual. Mocked `speechSynthesis` also means the browser's own TTS engine is never exercised.
**Revisit:** If `test:e2e` flakes or the fresh-server model collides with worktree workflows, key the port per-worktree or add a CI job (`playwright install --with-deps chromium` + `build:index`). If visual regressions become the concern, add `toHaveScreenshot` image diffs. If a real-TTS check is ever needed, drive an actual supported browser instead of the mock.

## 2026-10-01 — `search-qol-improvements` stays entirely in `search-ui`; recent searches are explicit-submit and local-only

**Context:** Four independent search-surface improvements (recent searches, back-to-search scroll restoration, page reference on result cards, truthful Copy label) needed one OpenSpec change. Scroll restoration is a navigation concern, so `app-shell` was a candidate home for it; and recent searches introduce the app's first user-state store, which brushes against the no-accounts guardrail.
**Choice:** All four requirements live in the existing `search-ui` capability as `## ADDED Requirements` only (nothing existing changes, so no `MODIFIED`/`REMOVED`). `app-shell` was rejected because it owns route-agnostic shell chrome (error page, nav overlay, toast live region, install-prompt init); the search results view's async index/results lifecycle is route-specific. Back-to-search keeps the query in the URL and adds a SvelteKit `snapshot` for the scroll offset, applied only after results render (SvelteKit's own history restore runs at `client.js` `scrollTo` before the async list exists, so it clamps to the short document). Recent searches are recorded only on explicit submit (Enter/topic/suggestion/recents activation), never on debounced typing, and are `localStorage`-only under a namespaced key; the list is never transmitted/logged/synced, while re-running a recent entry is an ordinary search submit logged anonymously per PRD §7.4. Logic goes in two new no-import pure modules (`src/lib/search/recent-searches.ts`, `src/lib/search/result-label.ts`) so dependency-free `test:*` scripts can import them directly.
**Trade-offs:** `search-ui` grows to own both filter-chip presentation and result-card/recents behavior; acceptable for one surface. Explicit-submit-only recents means an as-you-type search is not recallable until submitted. Scroll restoration is "approximately" (a shorter re-render clamps) and `manual (browser)`-only because there is no headless browser.
**Revisit:** If `search-ui` grows unwieldy, split a `recent-searches` capability; if users expect as-you-type queries in recents, revisit the record trigger; if SvelteKit changes history-scroll timing to run after async content, the snapshot workaround can be retired.

## 2026-09-30 — Broadening passage links to every result was a `REMOVED`+`ADDED` spec delta, not `MODIFIED`

**Context:** Item 3 of `ux-qol-improvements` lets protected/snippet results expose their passage URL (the passage page already shows "Full text not available" + official link for non-`full-text` sources). The standing `passage-view` main spec carried a requirement with a scenario literally named "Non-full-text results do not gain a passage link" — the exact behavior being reversed.

## 2026-09-30 — Highlight scrolls center, not top, because the app header is sticky

**Context:** After `persist-passage-highlight` shipped, "View passage" scrolled the first `<mark>` with `block: 'start'`, which aligns the term's top to the viewport top — where the app's sticky header (`Nav.svelte:53`, `sticky top-0 z-40`, ~56px) covers it, so only the bottom half of the highlight was visible and the user had to scroll up. `block: 'start'` is generally correct in a page WITHOUT a sticky header, which is why the flaw wasn't obvious in review.
**Choice:** Scroll the first highlighted occurrence with `block: 'center'` (instant, after `focus({preventScroll:true})`) so it lands mid-viewport, clear of the sticky nav; the no-query fallback keeps its existing smooth `block: 'start'` scroll to the ringed passage. Centering also degrades safely: when the scroll clamps (short document / mark near the end), clamping places the mark *below* center, so it can never be occluded.
**Trade-offs:** Centering is not pixel-exact when there is insufficient content above the mark (it clamps to 0), but the page's back-link + citation header occupy that space so the term still clears the header. The fallback path still uses `block: 'start'` and can sit ~40px under the nav (pre-existing, not addressed here).
**Revisit:** If the header stops being sticky, `block: 'start'` (or a `scroll-margin-top` matching the header height) may be preferable; if the no-query fallback is reported as occluded, apply the same header offset or center it too.

## 2026-09-30 — Client-side navigation resets scroll after render: position from `afterNavigate`, not a render-time effect

**Context:** `persist-passage-highlight` shipped focus/scroll inside a `$effect`-driven load path. Manual verification found a real bug: search → "View passage" landed at the TOP of the passage page, while refreshing the same URL worked. Cause (verified in SvelteKit 2.68.0 `src/runtime/client/client.js`): on client-side navigation SvelteKit renders, then resets scroll (`scrollTo(0, 0)`, `:1999-2014` — "we reset scroll before dealing with focus"), and only afterwards runs `afterNavigate` callbacks (`:2042`). A render-time effect scrolls before that reset and is overwritten; a full load/refresh performs no navigation, so nothing resets it. `afterNavigate` also fires on the initial entry (`:735-739`, `type: 'enter'`, gated on hydration), so it is the hook that covers both paths.
**Choice:** Apply focus/scroll from `afterNavigate(async () => { await tick(); applyQueryFocusAndScroll(); })`, sharing one idempotent helper with the retained `loadPassage` call (needed because `afterNavigate`'s `'enter'` can fire before the async search index renders the passage). The helper no-ops when the target element is absent and makes a single scroll decision per call. Deliberately REJECTED: `disableScrollHandling()` (disables SvelteKit scroll handling app-wide, explicitly discouraged) and `data-sveltekit-noscroll` on the link (fixes only that link, leaves back/forward and chapter navigation inconsistent).
**Trade-offs:** The helper runs up to twice per navigation; that is harmless (same element, second `focus()` targets the already-active node, no second announcement) but means the code cannot be simplified to one call site without reintroducing a race. The behaviour is unverifiable headlessly, so it must be re-confirmed in a browser.
**Revisit:** If SvelteKit ever changes its navigation scroll ordering (or the app adds its own navigation-level scroll management), re-check the `:1999-2014` → `:2042` window; if a global scroll strategy is ever adopted, this local hook should defer to it.

## 2026-09-30 — Passage highlight scope: query terms only (synonym-only matches are not highlighted)

**Context:** Implementing `persist-passage-highlight`, the passage page highlights only what it can derive from the URL (`q` + `phrase`) via `derivePassageParams`. Search, however, also highlights SYNONYM terms (`analyzePassage(..., highlightTerms)`), so a full-text result matched only via synonym expansion (e.g. `q=god` surfacing a "Higher Power" passage) is marked in the search snippet but gets NO highlight on the passage page — it falls back to the existing scroll + target ring. An early design draft claimed search↔page parity "by construction", which review flagged as inaccurate for this case.
**Choice:** Keep the approved scope (URL persists only `q`/`phrase`); highlight the QUERY TERMS on the passage page with the same offsets/escaping as search, and record the synonym-only case as a known, deliberate limitation (design.md "Known limitation", with a revisit trigger). Not carrying the matched highlight terms in the URL is intentional, not an oversight.
**Trade-offs:** A synonym-only match loses its on-page highlight (a small UX inconsistency vs. the search snippet) in exchange for a smaller URL surface and no extra persisted state. Non-phrase quoted queries also diverge slightly (the page highlights each word; search treats quotes as adjacency) — the page is a SUPERSET of search highlights, so "every query term" still holds.
**Revisit:** If users report that synonym-only results lose their highlight, carry the matched highlight terms (or a `syn=`/`hl=` param) in the passage URL and pass them through `analyzePassage(..., highlightTerms)`; that is an additive scope decision.

## 2026-09-30 — Passage highlights reuse search's offset path; the KWIC "full-text" primitive clips

**Context:** Planning `persist-passage-highlight` (new capability `passage-view`): clicking "View passage" on a full-text result must carry the query, highlight the terms in the passage page's chapter view, and scroll+focus the first highlight. The obvious reuse was `extractTerms`/`buildFullKwic` (used for Quick Reference results) or `buildKwicFromOffsets(text, offsets, 'full-text', …)`. Review proved both wrong: `extractTerms` is a naive whitespace split (misses `Gods will` ↔ "God's will", `face-to-face`), and `buildKwicFromOffsets` routes `full-text` through `resolveWindow`→`fullTextWindow`, which CLIPS to 2 sentences around the first match (`kwic.ts` `SENTENCE_CONTEXT = 2`) — so it cannot render a whole chapter with every occurrence.
**Choice:** Highlight each rendered passage from the SAME search path — `analyzePassage(text, phraseTokens, keywords)` offsets — via a NEW exported whole-text renderer (`buildFullTextHighlight(text, offsets)`, or exporting the private `highlightByOffsets` at `kwic.ts:173`). Phrase mode is normalized TOKEN ADJACENCY (not a character substring). Add one shared exported `derivePassageParams(q, phrase)` so the passage page doesn't re-implement the private `parseQuery`/`termsFromText`. Persist state in shareable URL params `q` + `phrase=1`, mirroring `syncUrl`. Highlight only for `displayMode === 'full-text'` sources.
**Trade-offs:** One new exported renderer + one shared param function (small API surface growth) in exchange for highlight/scroll that cannot diverge from search and never clips. The page must not use the clipping KWIC primitive for chapter rendering, which is non-obvious to a future contributor — hence this record.
**Revisit:** If the passage page ever needs clipped context instead of the whole chapter, or if `buildFullTextHighlight` duplicates enough of `buildKwicFromOffsets` to justify a shared low-level renderer with an explicit `clip: boolean`.

## 2026-09-29 — DR teaser guard: empty teaser when a bounded window cannot be a strict subset

**Context:** Completing `fix-daily-reflections-formatting` task 1.1's "never returns the entry's full `text`", `enforceProtectedClip` in `src/lib/search/kwic.ts` (out of scope) has a floor: for a one-word text it returns the whole window, so `buildReflectionTeaser` could return a 1-word entry's full text. A window that still covers every word (e.g. a short entry whose leading/trailing whitespace keeps `window.end < text.length`, so the clip guard early-returns) can also equal the trimmed text.
**Choice:** Guard inside `buildReflectionTeaser` (`src/lib/corpus/reflection.ts`): count the trimmed words and return `''` for 0/1-word input; after building, discard the HTML when stripping tags/entities yields as many words as the full text. `kwic.ts` is untouched and the normal bounded path is unchanged for real entries.
**Trade-offs:** A 1-word (or otherwise degenerate) DR entry renders an empty, neutral teaser rather than any text — preferable to leaking a protected full text. The guard duplicates a tiny plain-text extraction instead of exporting one from the out-of-scope KWIC module.
**Revisit:** If `kwic.ts` gains a shared plain-text/window-coverage helper, or if DR corpus entries become legitimately one word.

## 2026-09-29 — Filter-chip badge contrast lives on a ring; the accent helper returns fill/onFill/ring

**Context:** Implementing `fix-filter-sources-badge`, the spec binds ≥3:1 to the badge **ring** against the chip fill (not the badge fill) and requires it in both chip states: selected (chip fill == badge fill == accent) and unselected (chip fill `#fff` light / `slate-900` dark). One ring color cannot satisfy all of those backgrounds: a white ring on the gold `#C8902A` accent is 2.81:1, and any single neutral that clears white (`L≤0.30`) or slate-900 (`L≥0.136`) cannot also clear a dark navy accent.
**Choice:** `resolveSourceAccent(accent)` returns `{ fill, onFill, ring }` where `fill` is the validated hex or fallback navy `#2C4A6E`, and both `onFill` (label) and `ring` are the same WCAG contrast pick between `#FFFFFF`/`#1A1A1A` against `fill` (white on the dark accents, `#1A1A1A` on the gold). The unselected chip uses an exported neutral `CHIP_SURFACE_RING = #78716C` (stone-500), which clears 3:1 against **both** `#fff` (4.80:1) and slate-900 (3.72:1); the ring is drawn with an inline `box-shadow: 0 0 0 1.5px …` so the 8px dot keeps its size.
**Trade-offs:** The label foreground and the ring are the same token (they happen to be the same best-contrast pick; a future divergence would need a second output). The unselected ring is a fixed neutral rather than theme- or accent-derived, which is deliberate — one value that works in both themes. The helper's `ring` is only the selected-chip ring; the unselected ring is the shared constant, asserted separately by the test.
**Revisit:** If a future accent makes `max(contrast vs white, contrast vs dark)` fall below 3:1 (it is ≥~4.17 for any color), or if the unselected ring needs to differ per theme for aesthetics.

## 2026-10-02 — DR sentence context is a new optional `contextSentences` registry field

**Context:** Daily Reflections (`concordance-only`, `contextWords: 8`) search snippets read as fragments (~11% of an entry). Expanding to whole-sentence context needed to stay registry-driven (AGENTS.md) and flexible enough for other `concordance-only` sources, without reinterpreting `contextWords`, which is still the word-bound knob for `snippet` sources. DR's date (`chapterRef`, e.g. `January 1`) is the entry's natural lookup reference and was shown after the `DR` short title.
**Choice:** Added optional `contextSentences?: number | null` to `Source`, parsed in `registry.ts` and optionally validated in `validate.js`; set `"contextSentences": 1` on `daily-reflections`. In `kwic.ts`, a `concordance-only` source with `contextSentences > 0` uses the new `concordanceSentenceWindow()` (whole sentences via `splitSentenceRanges`/`sentenceIndexAt`); sources without it keep `eachSideWindow()` (word-bounded). `enforceProtectedClip()` gained a sentence-aware branch: when a sentence window covers the whole text it drops a whole sentence on the side away from the anchor (a single-sentence entry falls back to the word-drop). `buildCitation()` gained an optional `date` that leads as `<date> · <source>`; `_rankAndGroup` passes `formatReflectionDate(passage.date)` and `chapterRef: null` for DR. All DR surfaces (result card heading, home card, `/reflection` fallback) render the date first.
**Trade-offs:** `full-text` (SENTENCE_CONTEXT = 2) and `snippet` clipping are unchanged. A short DR entry whose window would cover it in full shows only the matched sentence (the guard overrides the sentence target) — intended, and pinned by spec/tests. `corpus/sources.json` is hashed into the index version, so the change forces `pnpm run build:index`.
**Revisit:** If a second source needs sentence context, it just sets `contextSentences`; if `full-text` ever needs a configurable sentence count, generalize `SENTENCE_CONTEXT` into the same field.

## 2026-10-02 — Hardened the single-word protected clip and made the DR e2e bound structural

**Context:** Review of `dr-sentence-context-and-date-reference` found (a) `enforceProtectedClip` returned the window unchanged when `words.length <= 1` (pre-existing at HEAD), so a hypothetical one-word `concordance-only` passage could be rendered in full by the search-result path (`buildKwicFromOffsets`/`buildExcerpt`); and (b) the updated DR e2e asserted a numeric `< 120`-word excerpt bound the implementation does not guarantee (a clipped excerpt can reach ~146 words for some anchors), contradicting task 3.3's structural-assertion requirement.
**Choice:** Fixed both. (a) `enforceProtectedClip` now returns the empty neutral window `{ start: 0, end: 0 }` when a protected (`snippet`/`concordance-only`) passage has `words.length <= 1` — nothing is rendered rather than the full text. No test depended on the old return. (b) The DR e2e drops the numeric bound: it reads the matching entry's full `text` from the page's own `/index/passages.json` (derived from the visible heading's date), then asserts the copied excerpt is not the full text, contains `…`, normalizes to a verbatim run of the entry, and has strictly fewer words — structural and fixture-independent across all DR results.
**Trade-offs:** The single-word window is now empty (nothing to render) instead of the whole passage; the spec's "never renders the full passage text" is now enforced for that edge on the search path too. `full-text` and multi-word protected clipping are unchanged. The e2e's in-page index lookup is slightly more work but removes the magic number entirely.
**Revisit:** None — the edge is hardened and the e2e no longer carries a fixture-dependent bound.

## 2026-10-02 — Recovery reference texts: PD-only full-text sources; Concepts and the Eleventh prayer are protected
**Context:** User asked to add the Twelve Steps, long-form Twelve Traditions, Twelve Concepts, Ninth Step Promises, and step prayers as searchable sources, asserting all were "open source and reproducible legally." Recon found that premise is false for two of the five items: (1) the Twelve Concepts are marked "© 1962 Alcoholics Anonymous World Services, Inc." on aa.org in both short and long form (the long form sits in the copyrighted *A.A. Service Manual*), and are absent from the 2nd-edition Big Book entirely; (2) the commonly-read "Eleventh Step prayer" ("Lord, make me a channel of thy peace…", a St. Francis adaptation) is Twelve Steps and Twelve Traditions p.99 — protected `snippet` text — not Big Book text; the Big Book carries only the Third (p.63) and Seventh (p.76) Step prayers. The Ninth Step Promises and the Third/Seventh prayers are genuine public-domain 2nd-edition Big Book text.
**Choice:** Change `add-recovery-reference-texts` adds four registry-driven sources with no app code changes and no new route/page — `twelve-steps` (full-text, PD), `twelve-traditions` (repurposing the existing disabled slot into the long form, full-text, PD), `promises-and-prayers` (full-text, PD only: Ninth Step Promises + Third + Seventh prayers), and `twelve-concepts` (registered but **disabled**; enabled as full-text only once a written reproducible basis — AAWS permission or a verified non-renewal — is documented in `corpus/CORPUS-GUIDE.md`, per the guide's rule never to render full text without a documented basis). No `snippet` fallback for the Concepts. The Eleventh prayer is **not** added as a new source; it remains reachable through the existing `twelve-steps-traditions` snippet source. All full-text additions record their PD basis in `CORPUS-GUIDE.md` and the registry before rendering. Discovery stays on existing surfaces (dynamic source-filter chips, `/sources` cards, indexed passage `title`/`chapterRef`).
**Trade-offs:** Two of the user's requested items ship gated or not-at-all as new full-text sources, so the catalog is smaller and more conservative than the request implied; the Twelve Concepts requires a separate legal/permission step before it can be enabled, and the Eleventh prayer is only discoverable via the 12&12 snippet rather than as a named full-text prayer. The PD Promises/prayers duplicate Big Book passages already indexed (provenance is labeled; de-duplication is explicitly not promised). Updating the stale `promises` known-exception hint requires editing `corpus/known-exceptions.json`, whose app-bundled mirror lives in `src/lib/corpus/exceptions.ts` (a deferred `src/` follow-up).
**Revisit:** If AAWS grants written reproduction permission for the Twelve Concepts (or a non-renewal is verified), enable `twelve-concepts` as full-text. If the `twelve-steps-traditions` (12&12) copyright is resolved, reconsider surfacing the Eleventh prayer as its own source. If users find the PD/Big-Book duplication confusing, revisit grouping or de-duplication.
